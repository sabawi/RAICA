# CHANGELOG v1.0.0.306 — one rule about output, stated twice, naming the channel

**Date:** 2026-08-17 · **Against:** v1.0.0.305 · **Closes:** SI-071

## The failure

`❌ No tool calls generated by the tool calling model` — then the primary model answered with no
data and **fabricated** figures: `n = 78 events` against a file holding **225**, complete with a
LaTeX derivation and an invented sum.

The raw response shows the model did nothing wrong:

```
"tool_calls": [],
"content": "```json\n[\n  {\"name\": \"get_the_secret_tool\", \"arguments\": {}},\n
             {\"name\": \"lookup_website\", \"arguments\": {\"url\": ...
```

It selected the right tools, in valid JSON, exactly as instructed — *"OUTPUT REQUIREMENT: Valid
JSON array of tool calls. Nothing else."* It typed them into `content`. The engine reads only
`tool_calls`, so a perfect selection was discarded unread.

**The instruction and the transport wanted different things.** "Produce a JSON array" is fully
satisfiable as text, and text defeats the mechanism.

## Not new — and the wording was the amplifier

`No tool calls generated` appears in **every archived log back to 08/16**, 3–11 per log. The latent
conflict was always there. Strengthening the directive to *"NO PROSE AND Nothing else but valid
JSON ARRAY"* raised compliance with the wrong reading to **100% (0/5)**.

**Six statements** described the output, and they disagreed with each other. The subtlest sat in
ABSOLUTE FAIL CONDITIONS:

```
- Generate any non-JSON text.
```

which does not forbid JSON text — it **licenses** it.

## The fix

Remove every output rule from the middle of the document. Keep exactly **two**: a boxed block at
the top and a restatement at the bottom. Both name the **CHANNEL**, never a format:

> Your selections must be issued as TOOL CALLS through the tool-calling interface. That is a
> CHANNEL, not a text format. … Anything you type as a reply — prose, a bare list, or a ```json
> block containing perfectly correct tool calls — is DISCARDED UNREAD. Nothing runs, the answering
> model receives no data, and it then invents figures.

The top block declares its own uniqueness, so the next person adding a tool section is told not to
add a seventh copy:

> This rule appears exactly TWICE in this document — here, and at the very end. Nothing between
> them describes your output format, because there is no output format to describe: there is only
> the channel.

`O - OUTPUT STRUCTURE` is retitled `O - WHAT EACH RESPONSE MUST CONTAIN (for the output CHANNEL,
see the top of this document)` — it keeps its symbolic-reference and dependency content and can no
longer re-acquire a format rule.

## Measured, four structures, same five prompts

| structure | tool calls | discards |
|---|---|---|
| "NO PROSE… valid JSON ARRAY" | **0/5** | 5 |
| one statement fixed | 3/3 | 0 |
| all six aligned | 4/5 | 0 |
| **two statements, top + bottom** | **5/5**, then **5/5** | **0** |

**10 consecutive clean runs**, 0 discards, 0 compute rejections, 0 `sandboxed_executor` for
arithmetic.

Consolidating beat aligning. Alignment removed the contradiction; consolidation removed the
ambiguity about where the rule lives — and left the file simpler, 16 scattered lines lighter.

## The control that prevented a wrong conclusion

Mid-investigation my own prose edits looked responsible: P1 went 2/3 → 0/3 right after them. A
control run on the **restored pre-edit prompt** also scored **0/3** — proving the edits were not
the cause and stopping a revert of correct work. Without that control the session would have
ended by deleting the fix and keeping the bug.

## Verification

Tier-0 **10/10**, version sync **19/19**, two independent 5-run rounds at 5/5. File integrity
checked against a backup: 16 lines removed, **all** output-related, nothing else touched.

## Residual — wording moves odds, code removes failures

A provider can drift back to `content` at any time and the failure is silent fabrication. The
durable fix is code: when `tool_calls` is empty and `content` parses as a valid array of
`{name, arguments}`, use it. **Not implemented.** Also unguarded: when zero tools run, nothing
stops the primary model inventing figures — that guard belongs in the primary prompt.
